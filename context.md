## 📋 Executive Summary
**NovaChat** is a high-performance, real-time messaging application designed to demonstrate modern web engineering practices. Built with a **React** frontend and a **Node.js/Express** backend, it utilizes **Socket.IO** for persistent, bidirectional communication and **Redis** as a unified data layer (handling session caching, active presence tracking, and chat message streams). Media assets, such as user avatars, are offloaded to **Cloudinary** cloud storage.

### 💾 Slide 5: Redis - The Heart of NovaChat
* **Slide Title**: Leveraging Redis Data Structures
* **Core Bullet Points**:
  * **Redis Hashes (`user:${username}`)**: High-speed storage for user profiles (hashed passwords, creation date, bio, avatar URLs).
  * **Redis Strings (`session:${sessionId}`)**: Fast session validation with a Time-To-Live (TTL) auto-expiry.
  * **Redis Sets (`online_users`, `user_chats:${username}`)**:
    * `online_users`: Tracks unique online usernames with constant-time lookup.
    * `user_chats:${username}`: Tracks a list of unique contacts the user has established a direct conversation history with.
  * **Redis Streams (`chat_stream:*`)**: Chronologically logs and assigns IDs to public and private messages.
* **Suggested Visuals**: Icons representing Hashes, Strings, Sets, and Streams showing how they map to NovaChat's database requirements.
* **Speaker Notes**:
  > *"Redis is often used solely as a cache, but here it is our database. We utilize its specialized data structures. Hashes store user profile records. Strings handle active sessions with automatic TTL expiry. Sets manage online presence, and Streams act as an append-only log of messages, giving us high-write throughput and simple history retrieval."*

### 💬 Slide 6: Message Persistence & Streams
* **Slide Title**: Persisting Chat History with Redis Streams
* **Core Bullet Points**:
  * **Chronological Logs**: Redis Streams automatically tag each entry with a millisecond timestamp ID (e.g., `1685892000000-0`).
  * **Retrieval (`xRevRange`)**:
    * API fetches historical messages backwards, beginning with the latest.
    * Client displays them in order, ensuring instant scroll back.
  * **Scalable Private Keying**: 
    * Private chat stream keys are derived using alphabetically sorted usernames:
      `chat_stream:private:alice:bob`
* **Suggested Visuals**: A graphic representation of an append-only message stream growing left-to-right, with timestamps.
* **Speaker Notes**:
  > *"To support message history without a relational database, we use Redis Streams. Each message is appended to the stream with a timestamp ID. To retrieve global history, we call XREVRANGE to fetch the latest messages and display them. For private 1-on-1 chats, we sort the two usernames alphabetically to generate a deterministic key, ensuring both users read and write to the same stream."*

### 👤 Slide 7: Profile Customization & Media uploads
* **Slide Title**: Stateless File Management
* **Core Bullet Points**:
  * **The Challenge**: Storing images on the application server makes it stateful, preventing horizontal scaling.
  * **The Solution**: 
    * **Multer** parses incoming multipart form uploads on the Express backend.
    * Media is directly uploaded to **Cloudinary** using its Node.js SDK.
    * Cloudinary returns a secure CDN URL, which is written to the user's Redis Hash (`user:${username}`).
* **Suggested Visuals**: Flow chart: User App -> Express (Multer) -> Cloudinary CDN -> Redis Database URL save -> User App.
* **Speaker Notes**:
  > *"When a user uploads a new profile picture, we parse the form data using Multer. The file is streamed straight to Cloudinary. Once Cloudinary hosts the image, it gives us a secure CDN URL. We write this URL to the user's profile Hash in Redis. This keeps our backend stateless, meaning we could spin up ten server nodes without worrying about syncing local upload folders."*

## ❓ Technical Talking Points & FAQ for Reviews

### 1. Why use Redis Streams instead of a traditional relational database (SQL) or MongoDB?
* **Latency**: Redis operates entirely in memory, offering sub-millisecond read/write capabilities.
* **Stream Primitive**: Redis Streams are specifically optimized for message logs, supporting automatic chronological indexing and simple querying.
* **Concurrency**: Relational databases can experience lock contention under high-frequency writes. Redis handles concurrent operations single-threaded in memory, preventing race conditions.

### 2. How is horizontal scaling achieved for Socket.IO?
* If we deploy multiple instances of NovaChat backend behind a load balancer, client connections will be split across different servers.
* **Solution**: We can attach a **Redis Adapter** to Socket.IO. The adapter uses Redis Pub/Sub channels to broadcast messages across all backend server nodes, ensuring a user on Server 1 can seamlessly chat with a user on Server 2.

### 3. How does session handling work without JSON Web Tokens (JWT)?
* Instead of stateless JWTs (which cannot be revoked easily before they expire), NovaChat uses session tokens cached in Redis (`session:${sessionId}`).
* This allows instant, server-side session revocation during logout, and the `SESSION_TTL` environment variable ensures inactive sessions clean themselves up automatically.
